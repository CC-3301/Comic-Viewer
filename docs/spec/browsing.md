### 浏览与排序

9. 作为漫画读者，我想在浏览列表看到每个条目的封面，以便一眼认出漫画
   - 书取其第一页
   - **容器取其本层首图**
   - 多子文件夹的文件夹逐级下取（每一层按同一套优先级：本层图 → 本层首个压缩包的首帧）
10. 作为漫画读者，我想按名称自然排序浏览，以便 APP 里的顺序和我电脑上整理的完全一致
    - 规则与 Windows 资源管理器一致
    - 特殊字符先于数字、数字先于字母、假名先于汉字
    - 数字按数值比较（第2话 < 第10话）
    - 字母不区分大小写
    - 假名按五十音序（平假名与片假名同权）
    - 汉字按拼音
11. 作为漫画读者，我想按修改时间排序（文件 mtime），以便定位最近更新过的内容
12. 作为漫画读者，我想按发布时间排序（书的发布日期，来自 CBZ 内 ComicInfo.xml 的
    Year/Month/Day），以便按出版顺序阅读
13. 作为漫画读者，当书没有发布日期元数据时（如图片文件夹），发布时间排序应回退为修改时间排序，
    以便排序始终可用
14. 作为漫画读者，我要求全部四种来源都支持名称/修改时间/发布时间三种排序，以便体验一致
    - Komga 的发布时间排序走服务器端 sort，修改时间用服务器记录的文件修改时间
    - **排序方式与方向是全局一份设置**
      - 三种排序各自带方向（默认：名称升序、时间类新→旧）
      - **排序菜单给恰好 6 个显式选项（类别 × 方向）**
      - 点一项即类别与方向同时生效（不再有「点当前类别再点一次即反向」）
      - 当前生效项打勾、按钮文字写当前类别与方向
      - 选定后跨目录层级、跨连接、跨重启保持，浏览列表与书柜柜内读写同一份
    - **例外**：Komga 的「阅读过」入口固定按最近阅读倒序，见故事 15
15. 作为漫画读者，我想在 Komga 来源按
    **四个入口（收藏 / 系列 / 书籍 / 阅读过）→ 收藏或系列 → 书** 的结构浏览，
    以便符合 Komga 的组织方式
    - 起始层由连接表单的「路径」决定，逐级返回一路回到路径起点
    - **有意例外**：「阅读过」固定按最近阅读倒序，不跟随排序菜单的类别档
16. 作为漫画读者，我想在浏览列表看到已读书目名称正下方的进度条，以便了解之前读到哪里
    - 在名称那一列内、与名称左缘对齐；网格档则是压在封面下缘
    - 部分填充绿色 = 进行中，满格红色 = 读完
17. 作为漫画读者，在混合目录（既有图片又有子文件夹）中我想点击图片条目后从该图开始
    按自然排序连读本目录图片，以便灵活入书
    - 混合目录因此是**容器**：点它先进浏览列表
18. 作为漫画读者，在混合目录中我想点击含图片的子文件夹后按顺序阅读它，
    以便直接进入那一话
    - 只含图片的子文件夹才是书，在列表里直接打开
19. 作为漫画读者，我想在浏览层级间前进/后退，以便快速往返于层级 A/B 之间
    - 全面屏返回手势与鼠标后退侧键 = 后退
    - 前进侧键 = 前进
22. 作为漫画读者，我想用鼠标滚轮在 APP 的各个列表界面滚动，以便不碰屏幕也能浏览

## Implementation Decisions

### 名称自然排序比较器

独立纯函数模块，用于文件目录、CBZ 内部、相邻书判定
（**比较规则见故事 10**；本段只记限制、探针与已知偏差）。

**已知限制**：以下各条只登记、不追平。

- 汉字段用 JDK 的中文 Collator，其字表与 Windows NLS **逐字不同**
  - GB2312 表内字同样可能中招、表外字被整块排到汉字末尾
- 另有三个次级根因：
  - **假名段与汉字段的段边界**（本实现按 run 切分，Windows 按逐字符类优先级）
  - **假名浊音**（JDK 日语 Collator 在 primary 层把 こ/ご 同权，Windows 是 こ < ご）
  - **符号段内的空白**（本实现当同段字典序比较，Windows 视空白可忽略）
- 差异幅度以本地探针输出为准，不写死数字（样本或比较器一变即需重新标定）
- 追平需自造汉字权重表并重做假名段规则，另行开票

### 浏览列表按需加载（票 #119 步骤 3）

**首帧**：

- 浏览页**正向档**首屏先落已有快照当首帧（`Source.snapshotEntries`，0 请求）
- 两条路：
  - 文件源 = **落盘的列表快照**（见「列表快照落盘」）
  - Komga = **会话内列表**：内存一份、不落盘、不含 mtime，
    **不是**词表里的「列表快照」（词表那条含该目录自身 mtime 与落盘，
    见 `CONTEXT.md`）
- 随后按这一帧的长度与**恢复到的滚动索引**中的较大者为下限**连续取够页再替换它**
  - 因此返回浏览页时列表不少于原位置所需长度
  - 取到的页里出现空页即当终止，不再往后取
- 滚到列表尾部再取下一页；服务器排序即最终顺序的层可一直滚到底（不受 1 万条上限截断）

**列表快照只当首帧**：

- 快照**整份上屏**，**不是第二个数据来源**
- 它只与「恢复到的滚动索引」一起决定首屏要取够多少条
- 取数只有 `Source.listEntriesPage` 这一条路

**逐页与整层必须同序**：

- `Source.listEntriesPage(containerId, sort, page, size)` 逐页拼起来的结果
  与 `listEntries` 在**同一 (containerId, sort)** 下逐字同序
- 默认实现 = 全量后切片（文件源没有服务端分页）
- Komga 只在「服务器排序即最终顺序」的档位按页直取服务器：
  修改时间 / 发布时间 / 「阅读过」全天 / 某系列的书的那两档
- 名称档与收藏/系列列表回退默认实现
  （要按 Windows 名称序本地重排，逐页直取会打乱全局顺序）
- **回退档的整层枚举在一次浏览会话内只做一次**
  （结果进会话快照，后续页从它切片，下拉更新才重枚举）
- 因此名称档（默认排序）仍整层取数、受 1 万条上限并给提示
- **Komga 的名称档首帧不允许空白等整层**只对「会话内已枚举过这一层」成立
  （先落会话内列表那一帧）
- **冷启动**（进程重启后首次进这一层、会话内没有快照）仍要等整层枚举；
  消解需给 Komga 落盘列表快照（新机制，未做）

**起始路径（`browsePath`）**：

- 落在上述任一层的连接（`/read`、「书籍」、「某系列」）走同一套判据
- 能直取的照样直取：`/read` **不分排序档**都直取（与上文「阅读过全天」同一档）
- `/books` 与 `/series/<id>` 只在非名称档直取，**名称档照旧整层取**
  （要按 Windows 名称序本地重排）

**直取档的取数下限**：

- **直取档的会话内列表只含第 0 页**
  ⇒ 这一帧可能短于离开前
- **取数下限 = 「快照长度」与「恢复到的滚动索引 + 1」中的较大者**
- 两档的滚动位置都以**项坐标**记（网格档一项 = 一格）
  （条目 + 截断提示行 + 尾部触发件行）
  - 网格档给的是首个可见**行的首个格子**、行号 = 项索引 ÷ 列数，界面不做换算
- 从这个下限连续取够页再替换 ⇒ 上文「列表不少于原位置所需长度」对直取档同样成立
- 续页照旧靠滚到底
- 恢复索引是**下限不是请求数**：来源说没有下一页（或出现空页）即停，请求数仍有界

**正向档取够之后还要把位置放回去**：

- 反向档是整份取完再翻转、不做显式放回（见段末）
- **首帧就是会话快照**：滑入的头几帧列表不为空
  - **例外（票 #111 ①）**：只有**「进阅读器」那一档**的滑动过渡里，新屏画的头 `ENTERING_SHELL_FRAMES`(=2) 帧是
    **主题底色壳**、正文（含那一帧列表）随后才挂 —— 「点了先愣一下」空档的修法，见 `docs/spec/shell.md` 的「导航过渡」段。
    列表**数据**仍是会话快照（下面几条的承诺不变），只是那 1–2 帧还没画出来；**返回档（出阅读器）的新屏当帧挂正文**。
  - **导航前预置目标层（票 #111 ②）**：下面这四类导航在换屏前先预置目标层的列表快照 —— 点条目下钻 / 进连接根层 /
    启动重建 / 鼠标前进侧键（前进侧键从阅读器过来时是滑动档，预置对它一样成立）⇒ 新屏出生当帧就有内容。
    **换书不适用**（它没有目标浏览层，新屏是阅读页）；**返回上级 / 系统返回也不预置**（系统弹栈，没有应用层入口；
    它的首帧照旧来自该层自己此前枚举留下的列表快照，**例外见下面的「代价」段**）。
    写入口径、代价与顺序防线见下面「同步快照访问器」段。
- 而恢复索引的读必须在**任何一帧列表上屏之前**完成（否则首帧那份短列表会先把索引夹小、再也取不回来）
  ⇒ 离场那一刻记下的索引与当下读到的索引**取较大者**（判据本身不碰界面状态）
- 返回时首帧那份短列表已让 `Lazy` 把恢复的索引夹到已加载末尾
  （票 #146 之前的实测：恢复是首帧之后 `requestScrollToItem` 跳过去，才被夹到已加载末尾；
  当时日志里那个具体索引取决于首帧项数与屏上可见条数，从代码重建不出来，故只留结论——
  现在改由下一条的组合期初值先落位）
- **首帧初值 = `min(本代次的位置记录, 首帧项数 − 1)`，下界 0**（票 #146；首帧还没有列表时取 0）：
  「本代次的位置记录」= **启动那一代取盘上那条一次性记录**（`ui/BrowseScrollDiskStore.kt`），
  其余代次取内存记录（票 #142 b13 修正入参口径）；两档滚动状态在
  **组合期**就拿这个值建，首帧即落原位；记录长于首帧时由下面那条「取够页后显式滚回」接手
  （两条是同一条恢复链的两半）
- 列表涨长不会自己回去 ⇒ 取够页后界面**显式滚回恢复索引**
  - 当前位置已经不小于它、或这一层没那么长时不动
  - **下拉更新与重试后按当下位置重算**，否则在顶部刷新会被拽回上次恢复的位置

**代价**：

- 直取档的**整层枚举不再写这份会话内列表**
  （同一 (容器, 排序) 上，整层枚举与第 0 页共键而长度差一个数量级，
  写进去会让方向切回正向时首屏按整层长度取页、发 ⌈N/每页⌉ 次请求）
- 因此**反向档**在直取层上从阅读器返回、**且该键还没被第 0 页写过时没有会话内首帧**：
  先显示「加载中…」，等这次整层枚举跑完才上屏
  - 反向档每次进入本来就要整份取完再翻转，请求数不因此增加
  - 该键被正向第 0 页写过时仍给出一帧，只是长度 = 第 0 页
- 正向档不受影响（第 0 页帧照旧）
- 这一条也是「同步快照访问器」那节「从阅读器返回浏览页时列表立即可见」的适用范围限定
- 让两种档各有各的键需要把方向带进 `Source` 的会话列表接缝
  （方向现属展示层概念），留作新决策

**反向档仍是整份取完再翻转**（按需加载只对正向档成立）：

- 方向是展示层概念、施加在整份列表上（见「排序在展示层翻转」）
- 追加页只能往尾部接，复现不了「从尾到头」

### 封面

**取哪一张**：

- 书 = 第一页
- **本层有图的容器 = 本层首图**
- 多子文件夹的文件夹 = 逐级下取
  - **每一层都与单层目录同一套优先级**——本层图 → 本层首个压缩包的首帧
  - 每层只开首个包，同层其余包不碰

**预取**：

- 封面**字节**由界面按需取
- 列表/柜页对**可见区 ±1 屏**内、**且封面走来源字节通路**的条目**主动预取**
  - **取字节有并发闸**（票 #145）：同时最多 **4** 张在飞，可见格**优先取牌**、预取在排队时让位
    （已经在飞的往返不抢占；**解码不进这道闸**，闸的只是「同时向来源发几次请求」）
  - 预取**派发分批**上限仍是 **4** 条（`CoverPrefetch.MAX_CONCURRENT_LOADS`）——那是「一批发几条任务」，
    与上面那道闸（「同时在飞几张」）**不是同一个量**，两者各自独立生效
  - 出屏不立即淘汰
  - 走 uri 解码的本地/SAF 封面行不预取
- 预取 = **取字节 + 解码进封面位图分区**，与可见行**同一把解码键**
  （就绪后可见行直接命中，不再重解、也不重复取同一份字节）

**何时发生**：

- **容器封面的逐级下取与压缩包首页封面的解出都只在按需取封面时发生**，
  枚举期一次都不发生
- 缓存分两层：
  - 压缩包封面解出的首页按「node.id + 修改时间」**落盘**缓存
  - 所有封面字节（含目录/容器封面）另有**会话级内存字节缓存**
    （键含条目 id 与 mtime，条目数与字节数双上界，手动刷新与来源实例释放时清空）
- 探测「这个子目录是不是书」时已知的「目录内首图」直接用于封面，不再重复列同一目录

**容器行封面兜底（Komga）**：

- 取不到缩略图的容器行（类别行、收藏行等）按**本地 Windows 名称序**（与列表同一套比较器）取**第一个子项的封面**
  （候选取服务端名称档的一页 500 条，超出这一页的条目看不见、按服务端序退化）
- 子项也没有则留空
- 该封面**不随全局排序变化**
- 收藏内容非纯系列时，其**内容行**也按同一套本地 Windows 名称序重排（封面与列表第一行因此是同一本）

**Komga 源取哪一张（票 #140）**：

- **书封面 = 第 1 页原图**（`GET /api/v1/books/{id}/pages/1`），**不带任何查询参数**
  （票 #145 曾带 `convert=webp`，2026-09-28 回滚：该服务器的 `convert` 枚举只有 `jpeg|png` ⇒ webp 回 400
  ⇒ 整屏 Komga 封面全灰）
- **系列封面 = 该系列按本地 Windows 名称序第一本书的第 1 页**
  （列表显示用的就是这一套；服务端 `titleSort` 字符串序只用来取候选页、不作判据——实测它会挑到另一本书，票 #140 2026-09-27 真机回报）
- 容器行（类别 / 收藏）仍按上面的兜底链取第一个子项的封面
- **不再用服务端的 `/thumbnail`**：实测它按**高 300px** 固定生成（宽 200–217），
  而**测试设备**（屏宽 ≈1272px）上网格 2 列的解码宽度是 **576px** ⇒ 放大 **2.7 倍**，这就是 Komga 源封面糊的来源
  （576px 是那台设备的桶值：屏更窄/更宽时按同一条分桶口径算出别的数，代码里没有这个常量）
- 代价：
  - 字节变大（每张从几十 KB 到数百 KB 级；实测一张 1272×1800 的页 **429,892 字节**，解码冷 613ms / 暖 22ms；
    见票 #140 的证据段 —— 量它那条用例单一跑 1m26s–1m45s，维护者 2026-09-27 裁定**不进套件**）
  - 长条漫首页要按显示盒裁剪解码（票 #81/#85 的裁剪解码就是为这类源做的）
  - **容器行（系列 / 类别 / 收藏）每跳多一次 list 请求**：取封面要「先 list 出名称序第一项、再取它的第 1 页」，
    旧口径命中服务端 `/thumbnail` 时是 1 次请求
  - **会话级封面字节缓存的字节上界从 8 MiB 提到 32 MiB**：`core/source/CoverByteCache.kt` 的上界是条目 64 / 字节 **32 MiB**
    （票 #145：按上面的实测字节量级，8 MiB 只装得下约 15~19 张、一屏 12 张就顶满，冷启动头几秒必然重取；
    32 MiB 装得下约 60~78 张 ≈ 4~5 屏。条目数上界 64 与它同量级（64 × 430~537 KB ≈ 27~34 MiB）
    ⇒ **哪一边先触顶取决于封面字节大小**，两档的实际容量都在 60 张上下）

**缩放策略**：

- 浏览**列表档**的封面按**自身宽高比铺满行内封面列宽**
  - 56dp 不变；高度 = 宽度 × 比例，完整显示不裁剪
  - 解码前按占位比例避免列表跳动
- 浏览**网格档**的格子是**统一尺寸**
  - 格宽由设置列数等分、格高 = 格宽 × 固定格比例
    （高宽比 4:3 常量、与封面自身比例无关）
  - 封面在格内**裁剪填满**（短边铺满、长边裁掉）
  - 因此任何比例（含超长条漫页、超宽跨页）都不改变格高、不留灰边、不出现「半截」
  - 但**格子高度上限 = 可视高 − 名字行高**（横屏 2 格等场景），
    超限时封面**等比收窄并水平居中**（盒比例仍 4:3、不拉伸），名字行始终可见
- 两档都**按本次显示宽度解码**
  （调用方给的 dp→px 向上取到 32px 整数倍分桶，解码缓存键含目标宽度）
- 比例超出兜底区间（高宽比 0.6–1.6）时按限值盒子填充裁剪（**列表档专用**；网格档一律裁剪填满）

**按显示盒裁剪解码**：

- 解码前先取源尺寸，按本次显示盒算出源坐标上**居中**的可见带，只解这一条带
  - **API 28+** 裁剪解码与缩放一步完成
    - **目标尺寸不许 clamp**——目标尺寸与裁剪矩形是一套映射，改小就取不到那条带
  - **API 26/27** 退回区域解码再缩到显示盒宽度，只缩不放
- **走带必须同时满足四条**：
  1. 带真的裁掉了像素
  2. 保留位图更小
  3. 带的瞬态峰值 ≤ 12.8MB
  4. 裁剪解码那条带同时轻过区域带与整图子采样
  - **①②③ 任一不成立就沿用整图子采样**（④ 只决定两条解码器里选哪条）
- **约束：保留位图从不比改动前（整图子采样）大**
- 峰值口径只数解码器要建的那几张位图，**真机 RSS 峰值实测未做**
- 阅读菜单的预览条与三档字号层级见 `docs/spec/reader.md` 的「阅读菜单与预览条」

### 列表枚举性能

**每层只列一次目录**：

- 文件源（本地/SAF、SMB、WebDAV）列目录时每层只列一次；子目录「是书还是容器」的属性探测
  **并发执行且有并发上限**
  - 单条探测失败降级为容器，不拖垮整表
  - 传输层故障例外：断链/认证失效照 `TransportFailure` 冒泡，不伪装成「都是容器」
- 同一目录在同一会话内二次进入命中会话级列表快照（会话级来源实例按连接复用）
  - **快照按容器一份、与排序方式无关**——换排序不再重列目录
  - 枚举结果保留列目录时顺手拿到的节点 ⇒ 名称/修改时间两档排序的比较器里没有任何 I/O
  - **发布时间档**在本次枚举里读包内 `ComicInfo.xml`，每个条目只算一次、按「条目 id + mtime」缓存
  - **落盘快照恢复的条目**（没有节点）在异步枚举落地前用快照里的 mtime 兜底，**不 resolve 也不开包**
- 文件改动按容器 mtime 失效（命中时花一次取节点比对 mtime，与条目数无关）

**mtime 变化不整层重探**：

- 仍只发 **1 次列目录**，把新结果与上次快照（会话内或落盘）按「条目 id + 该条目自身 mtime」比对
- 新增/删除/改名直接反映
- **子目录自身 mtime 变了只重探那一行**，未变化的行**沿用上次结论、0 次探测**
  - 两侧都取不到 mtime 的层（SMB 共享根、部分 SAF/WebDAV 层）视同「未变」
- 探测失败的结论一律不复用、只重试失败的那几条

**显式刷新入口 = 浏览页顶部的下拉更新**：

- 只认拖拽，滚轮一律不触发
- 动作为清该容器缓存并重取容器/压缩包封面（走 uri 解码的本地图片封面不重取）
- **它是强制路径：清缓存 = 下次进入整层重列 + 全量重探**，增量复用只作用于自动失效路径
- 它同时清该容器的**内存与落盘快照**

**相邻书（上一本/下一本）**：

- 判定复用同一份会话快照、**只读**；未命中时不列父层、不探测子目录
  ⇒ 该容器本次会话未被列过时两侧邻位均为 null，界面照故事 28 提示「无上一本/无下一本」
- 进阅读器后由界面在后台补齐该层
- **缓存失效只看容器自身**的 mtime ⇒ 仅子目录**内容**的增删不会自动反映
  （要靠下拉更新，或父目录自身 mtime 变化后的增量重探）

**列表快照落盘**（键 = 连接 id + 容器 id，APP 私有缓存目录）：

- 内容 = 条目清单 + 该目录自身 mtime + 写入时间 + 格式版本号，**不落盘封面字节**
- 退出 APP 后再进入同一目录：
  - mtime 未变 ⇒ **0 次列目录、0 次探测**
  - mtime 变了 ⇒ 先用快照把列表显示出来、再 **1 次列目录 + 增量重探**
- **先显示的那一帧由快照承担**，界面侧先落它、再落重列结果 ⇒ **静默刷新**：不闪空白、不打断滚动
- 每条快照判 **7 天 TTL**（看写入时间，不是最后使用时间）
- **取 mtime 失败**（离线/服务器不可达）仍用快照把列表显示出来
- 连接被编辑或删除时清该连接名下全部快照
- 容量上限 **2000 条或 20MB**（先到者为准，按最后使用时间淘汰）
- 格式版本号不匹配整片作废重来、不崩溃

**同步快照访问器**：

- 从阅读器返回浏览页时首帧直接落会话内快照，不列目录、不比对 mtime ⇒ 列表**立即可见**、不闪「加载中…」
  - **例外（票 #111 ①）**：只有**「进阅读器」那一档**的滑动过渡里，新屏头 `ENTERING_SHELL_FRAMES`(=2) 帧只挂主题底色壳、
    正文随后才挂；「数据这一帧就在」不变，变的只是那一两帧还没画（返回档的新屏当帧挂正文；
    见「首帧就是会话快照」那条的例外与 `docs/spec/shell.md`）
  - **列表快照多了一条写入口径（票 #111 ②）**：下面这四类导航在换屏前会先把**目标层的落盘快照**装进会话内那份
    列表快照 —— 点条目下钻 / 进连接根层 / 启动重建 / 鼠标前进侧键（前进侧键从阅读器过来时是滑动档，预置一样成立）
    （`Source.primeCachedEntries`：只读本地、不列目录、不探测）⇒ 新屏「出生」当帧就有内容。预置与导航本身在
    **同一临界区**里跑（进程内一把公平锁 `withPrimedLayer`），因此两次快速点击的落地顺序 = 发起顺序。
    **代价**：导航前多一次本地落盘快照读（在 `Dispatchers.IO`）；该层首次枚举的 `snapshotSource=` 因此可能是
    `memory`，而不是枚举期那条路的 `disk`（`snapshotEntries` 有意不写内存表，见 `DocumentTreeSource` 的 KDoc）——
    写它的是这条预置、不是枚举；0 次列目录 / 0 次探测的口径不变。写错层会让新屏显示另一层的内容，
    因此预置的键必须是**目标层**；读不到（来源未就绪 / 没有落盘快照，如 Komga）就是空操作。
    **不在这四类里的两跳**：换书（没有目标浏览层）与返回上级 / 系统返回（系统弹栈，没有应用层导航入口；
    它的首帧照旧来自该层自己此前枚举留下的列表快照，**例外见上面「浏览列表按需加载」一节的「代价」段**）——总述见 `docs/spec/shell.md` 的「导航过渡」段。
  - **例外**：直取层的反向档不写这份会话内列表，见「浏览列表按需加载」那节的代价段
  - 该键已被正向第 0 页写过时仍给出一帧
- 它**绝不做 IO**（在组合期被调用）

**冷启动（进程重启）首帧**：仍走异步路径，但分两段——先由快照给出一帧
（0 次列目录、0 次探测，只读本地文件），再落新枚举结果
⇒ **「加载中…」期间不再发生列目录/探测**。四个来源口径一致。
  - **Komga 为会话内列表**：内存一份、不落盘、不含 mtime，**不是**词表里的「列表快照」，
    **冷启动没有它**，见上文「浏览列表按需加载」
  - 键含排序方式

### 列表首屏与封面后到

- 列表在封面未就绪时即可见、可点
  - 封面按**可见区 ±1 屏预取**（取字节 + 解码）+ 可见行按需取
  - 口径见「封面」条
- 封面后到不阻塞名称与点击
- 但条目列表仍在**整批子目录属性探测完成**后一次返回
  （流式列表见 Out of Scope）

### 列表条目呈现与页数

**行内内容**：

- 浏览列表行内只有封面 + 名称（长名称最多两行）
- 没有「文件夹 / 书 · N 页」副标题

**进度条**：

- 已读书目的进度条在**名称正下方、与名称左缘对齐**（条右端到名称列右缘，不做内缩）
- 网格档则是**压在封面下缘、不占布局**
- 未读的书两档都不画、因此不留空白
- 条样式两档一致：轨道 = **主题前景色的 30% 不透明度**、
  **方头**端帽、高 **6dp**、不画 stop indicator
- **网格档**的条下另铺一层**黑 45% 暗底**
  （与条同宽同高、叠在封面下缘、不占布局；列表档没有；未读时暗底与条都不画）

**页数**：

- 文件源枚举期**不为页数**读压缩包中央目录、也不为页数列子目录
- 列表条目的页数一律为空，页数只在打开书后由 `BookHandle` 给出
- Komga 的页数来自服务器返回的 payload，照常返回但界面不显示

### 排序在展示层翻转

**来源接口不接方向**：

- 来源接口只接受排序方式、不接受方向（`Source.listEntries` 契约不变）
- 方向由界面按全局排序设置对来源返回的已排序结果**整份翻转**后展示
- 四个来源行为因此一致（例外见故事 14/15）

**设置存放**：

- 全局排序设置**（形态与选项见故事 14）**落 SharedPreferences（`ui/SortSettingStore.kt`）
- 条目列表只剩浏览页一处，因此它是浏览页的排序来源
- 「上次停留的位置」只记目录层级，切排序不改写它

**滚动复位**：

- **排序设置变化时浏览页两档滚动回到顶部**（票 #142 现行口径）
  - 复位只由排序设置的**写入**触发——**重新点当前已选的排序**（设置值与方向都逐字未变）也复位，
    实现见复位键里的 `SortSettingStore.revision`（票 #142 现行口径第 4 条）
  - 列表档与网格档各持一份滚动状态、各自复位
  - 换排序类别会重新枚举，新顺序落地那一帧会再复位一次
- **当次启动内**非排序变化不触发复位（下拉更新重列、切视图档位、进子目录/返回上级、
  从阅读器返回都照旧保持原位置）——本句说的是同一次启动里的导航；
  **重启**那一支是例外，分两种：
  - 落地层**不是**记录那一层时那条记录已被**当场丢弃**（见下条），此后走进记录那一层**不会再恢复
    重启前那一刻的位置**；
  - 落地层**正是**记录那一层时，**离开这一层、再从上一级进来 ⇒ 回顶部**（票 #142 现行口径第 2 条新写法）；
    登记条件是下述**两条同时成立**（任一单独都不成立）——两条都只看连接 + 容器与浏览链，
    与容器 id 形态无关（文档树来源的路径形态 id 与服务端 id 形态在这里一视同仁）：
    ① 写盘的那一层就是**此刻的浏览链顶**（= 用户此刻所处的那一层）；
    ② 记录那一层**已经不在浏览链上**（回退栈里浏览层的镜像）。
    因此落地层上「从阅读器返回」「进 / 出子目录」照旧按本句上面「**当次启动内**非排序变化不触发复位」
    那条保持原位置：进阅读器时写盘的是落地层**自己**（它在离屏时记自己的位置），那句「写盘的层 != 落地层」
    的早退先挡住（判据 ①② 根本没被求值）；进子目录时链顶是它的子层 ⇒ ① 成立，
    但落地层自己**仍在浏览链上** ⇒ ② 不成立；出子目录回本层同理（写盘层就是本层，同样被那句早退挡住）。
    只有「退回上一级」才会让上一级那一层**成为链顶并写盘**，且那一刻落地层已不在链上（两条同时成立）。
    作废以**一次**为限（再进来那一次起）回到那条口径。
    该判据仍依赖一个**时序前提**：上一级那一层要**组合并写盘**（`BrowserScreen` 的首屏写点）
    才会有那一次登记，少了那一次写盘就退回「保持原位置」（用户离开落地层后没在上一级停住、
    直接去了别处即此形态）。
    两个覆盖不到的情形（实现如实如此）：落地层是**根层**时这一条永不触发——根层之上那一级不是浏览层
    （书柜 / 设置等入口），没有浏览层会以链顶身份写盘；
    登记也不分去向——只认「链顶那一层写过盘」，因此从落地层回上一级再转去别处（如书柜）后回来
    同样会登记（那种去向不在本口径的授权范围内）。
- **重启恢复位置**（票 #142 现行口径第 2/3 条）：滚动位置**单独落盘一份**
  （`ui/BrowseScrollDiskStore.kt`），只存「上次停留那一层 + 该层位置」**这一条**、**用掉即清**
  （用掉 = 本进程内只喂启动那一代那一次；盘上那份仍留着，供**下一次**重启恢复）——
  落地层**还没交回**时（系统还原回退栈、界面先组合那一帧）问的正是记录那一层就先给值、不消费也不销毁，
  收口留到交回之后；
  **启动落地已定**那一刻收口：落地层就是记录那一层 ⇒ 停在原位置；
  落地层不是它 ⇒ **当场丢弃**那条记录，此后走进记录那一层**不会再恢复重启前那一刻的位置**
  （「重启后只有落地那一层有记录」）。
  落在记录那一层时，那条记录**只喂启动那一代**：收口之后本进程内不再交回任何层（收口只发生在那条记录
  指向的落地层上）；那条记录用掉之后，只有「离开这一层、再从上一级进来」那一种去向才作废该层的位置记录
  ⇒ 回顶部（口径见上面「**重启**那一支是例外」那两条）。
  「原 Out of Scope：滚动位置不落盘」这半句由票 #142 推翻，见 `docs/SPEC.md`「Out of Scope」。
  排序与位置都不进 `BrowseLocation`（它保持只记目录层级）
