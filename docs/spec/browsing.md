## User Stories

> 本册含故事 9–22。

### 浏览与排序

9. 作为漫画读者，我想在浏览列表看到每个条目的封面，以便一眼认出漫画
   - 书取其第一页
   - **容器取其本层首图**
   - 多子文件夹的文件夹逐级下取（每一层按同一套优先级：本层图 → 本层首个压缩包的首帧）
10. 作为漫画读者，我想按名称自然排序浏览，以便 APP 里的顺序和我电脑上整理的完全一致
    - 规则与 Windows 资源管理器一致
    - 特殊字符先于数字、数字先于字母、假名先于汉字
    - 数字按数值比较（第2话 < 第10话）
    - 字母不区分大小写
    - 假名按五十音序（平假名与片假名同权）
    - 汉字按拼音
11. 作为漫画读者，我想按修改时间排序（文件的修改时间），以便定位最近更新过的内容
12. 作为漫画读者，我想按发布时间排序（书的发布日期，来自 CBZ 内 ComicInfo.xml 的
    Year/Month/Day），以便按出版顺序阅读
13. 作为漫画读者，当书没有发布日期元数据时（如图片文件夹），发布时间排序应回退为修改时间排序，
    以便排序始终可用
14. 作为漫画读者，我要求全部四种来源都支持名称/修改时间/发布时间三种排序，以便体验一致
    - Komga 的发布时间排序走服务器端 sort，修改时间用服务器记录的文件修改时间
    - **排序方式与方向是全局一份设置**
      - 三种排序各自带方向（默认：名称升序、时间类新→旧）
      - **排序菜单恰好 6 项：3 种类别 × 2 个方向**
      - 点一项 = 类别与方向一起生效
      - 当前生效项打勾、按钮文字写当前类别与方向
      - 选定后跨目录层级、跨连接、跨重启保持，浏览列表与书柜柜内读写同一份
    - **例外**：Komga 的「阅读过」入口固定按最近阅读倒序，见故事 15
15. 作为漫画读者，我想在 Komga 来源按
    **四个入口（收藏 / 系列 / 书籍 / 阅读过）→ 收藏或系列 → 书** 的结构浏览，
    以便符合 Komga 的组织方式
    - 起始层由连接表单的「路径」决定，逐级返回一路回到路径起点
    - **有意例外**：「阅读过」固定按最近阅读倒序，不跟随排序菜单的类别
16. 作为漫画读者，我想在浏览列表看到已读书目名称正下方的进度条，以便了解之前读到哪里
    - 在名称那一列内、与名称左缘对齐；网格视图里压在封面下缘
    - 部分填充绿色 = 进行中，满格红色 = 读完
17. 作为漫画读者，在混合目录（既有图片又有子文件夹）中我想点击图片条目后从该图开始
    按自然排序连读本目录图片，以便灵活入书
    - 混合目录因此是**容器**：点它先进浏览列表
18. 作为漫画读者，在混合目录中我想点击含图片的子文件夹后按顺序阅读它，
    以便直接进入那一话
    - 只含图片的子文件夹才是书，在列表里直接打开
19. 作为漫画读者，我想在浏览层级间前进/后退，以便快速往返于层级 A/B 之间
    - 全面屏返回手势与鼠标后退侧键 = 后退
    - 前进侧键 = 前进
22. 作为漫画读者，我想用鼠标滚轮在 APP 的各个列表界面滚动，以便不碰屏幕也能浏览
55. 作为漫画读者，我想在浏览层点顶栏标题就地跳到连接起点或任意一级目录，
    以便不用连按返回键逐层退出，也不必为了横跳而反复进出
    - 菜单 = 连接起点层（文案 `/`）＋起点层的**全部**一级目录（不是只有当前路径上那一条）
    - 只列目录、不列书；一级目录全部列出、名称升序（菜单窗口 10 行，超出在里面滑）
    - Komga 的一级目录恒为四入口（收藏 / 系列 / 书籍 / 阅读过），与连接的起始路径无关；
      起始路径正好落在某一类本身时，那一项指回起点层（两者同一屏内容）
    - 停在起点层不弹菜单
    - 点「就是当前这一层」的那一项时**不跳转、改为刷新这一层**（不压出内容相同的一层）
    - 跳转后浏览链 = `起点层 → 目标`：从目标层返回回起点层（`/`），不回跳转前那一层

## Implementation Decisions

### 名称自然排序比较器

一个独立的比较函数，用在校内目录、压缩包内部、找相邻书这三处
（**排序规则本身见故事 10**；这一段只记「哪里和 Windows 不一样」）。

**已知偏差**：下面这些只登记，不修。

- 汉字用的是 JDK 自带的中文排序表，和 Windows 的表**逐字不同**
  - 常用字（GB2312 范围内）也可能排错位；生僻字会被整体排到汉字的最后
- 另外三个原因：
  - **假名和汉字的交界**（这里按一段一段切，Windows 按逐字符的类别优先）
  - **假名浊音**（JDK 把 こ 和 ご 当同权，Windows 是 こ < ご）
  - **符号里的空白**（这里当普通字符比，Windows 忽略空白）
- 差多少以本机跑一遍的输出为准，不写死数字（样本或比较器一改就要重新量）
- 要追平得自己做汉字权重表、重做假名规则，另行处理

### 浏览列表按需加载

本节反复用的三个名字，先说清：

- **正向**：排序方向与来源给的一致，可以一页一页往下要
- **反向**：方向与来源相反，必须把整层取完再倒过来
- **直取**：服务器排序就是最终顺序，可以按页直接要（不用等整层取完）

**首帧**：

- 浏览页**正向**首屏先落已有快照当首帧（`Source.snapshotEntries`，0 请求）
- 快照两条路：
  - 文件源 = **存在手机上的列表快照**（见「列表快照落盘」）
  - Komga = **内存快照**：只在内存、不落盘、不含修改时间，**不是**词表里的「列表快照」
- 随后按「这一帧的长度」与「要恢复到的滚动位置」里较大者为下限，**连续取够页再替换它**
  - 因此重新进屏时列表不少于原位置所需要的长度
  - 取到的页里出现空页就当到底，不再往后取
- 滚到列表尾部再取下一页；服务器排序就是最终顺序的层可以一直滚到底（不受 1 万条上限截断）

**列表快照只当首帧**：

- 快照**整份上屏**，**不是第二个数据来源**
- 它只和「要恢复到的滚动位置」一起决定首屏要取够多少条
- 取数只有 `Source.listEntriesPage` 这一条路

**逐页与整层必须同序**：

- `Source.listEntriesPage(containerId, sort, page, size)` 逐页拼起来的结果
  与 `listEntries` 在**同一 (containerId, sort)** 下逐字同序
- 默认做法 = 整层取完再切片（文件源没有服务端分页）
- Komga 只在「服务器排序就是最终顺序」的档位按页直接要：
  修改时间 / 发布时间 / 「阅读过」全部 / 某系列的书的那两档
- 名称档与收藏/系列列表回退默认做法
  （要按 Windows 名称序本地重排，逐页直接要会打乱全局顺序）
- **回退档的整层列目录在这一次打开 APP 期间只做一次**
  （结果进快照，后续页从它切片，下拉更新才重来）
- 因此名称档（默认排序）仍整层取数、受 1 万条上限并给提示
- **Komga 名称档首帧不空等整层**只对「这次打开 APP 已经列过这一层」成立（先落内存快照那一帧）
- **冷启动**（进程重启后第一次进这一层、内存里没有快照）仍要等整层列完；
  要消解得给 Komga 落盘快照（新机制，未做）

**起始路径（`browsePath`）**：

- 落在上面任一层上的连接（`/read`、「书籍」、「某系列」）走同一套判断
- 能直取的照样直取：`/read` **不分排序档**都直取（与上文「阅读过全部」同一档）
- `/books` 与 `/series/<id>` 只在非名称档直取，**名称档照旧整层取**（要按 Windows 名称序本地重排）

**直取时的取数下限**：

- **直取层的内存快照只含第 0 页** ⇒ 这一帧可能短于离开前
- **取数下限 = 「快照长度」与「要恢复到的滚动位置 + 1」里较大者**
- 两种视图的滚动位置都以**项为单位**记（网格视图一项 = 一格）
  （条目 + 截断提示行 + 尾部触发件行）
  - 网格视图给的是首个可见**行的第一格**、行号 = 项序号 ÷ 列数，界面不做换算
- 从这个下限连续取够页再替换 ⇒ 上文「列表不少于原位置所需要的长度」对直取层同样成立
- 续页照旧靠滚到底
- 恢复位置是**下限不是请求数**：来源说没有下一页（或出现空页）就停，请求数仍有限

**正向取够页之后要把位置放回去**：

- 反向是整份取完再倒过来、不做显式放回（见段末）
- **首帧就是内存快照**：刚滑进来的头几帧列表不为空
  - **换屏前提前装目标层的快照**：下面这四类导航在换屏前就装 —— 点条目下钻 / 进连接根层 /
    启动重建 / 鼠标前进侧键 ⇒ 新屏出生当帧就有内容。
    **换书不适用**（没有目标浏览层，新屏是阅读页）；**返回上级 / 系统返回也不装**（系统弹栈，没有应用层入口；
    它的首帧照旧来自该层此前列目录留下的快照，**例外见下面「代价」段**）。
    写法、代价与顺序上的防线见下面「提前装好目标层的快照」段。
- 而「要恢复到的滚动位置」必须在**任何一帧列表上屏之前**读到
  （否则首帧那份短列表会先把位置夹小、再也取不回来）
  ⇒ 离场那一刻记下的位置与当下读到的**取较大者**（这个判断本身不碰界面状态）
- 返回时首帧那份短列表已让 `Lazy` 把要恢复的位置夹到已加载末尾
  （早先是首帧之后 `requestScrollToItem` 跳过去才被夹住；现在改由下一条的初值先落位）
- **首帧初值 = `min(当前位置记录, 首帧项数 − 1)`，下界 0**（首帧还没有列表时取 0）：
  位置记录 = **启动后第一次进这一层用盘上那条一次性记录**
  （存在 `ui/BrowseScrollPosition.kt` 的 `BrowseScrollStorage`），之后换过排序设置则用内存里的记录；
  两档滚动状态在**排版时**就拿这个值建，首帧直接落原位；记录长于首帧时由下面那条「取够页后滚回去」接手
  （两条是同一条恢复链的两半）
  - 初值还带**顶部留白的折算**：被恢复那一项的**封面顶边贴视口上沿**；
    两档的差别见「排序在展示层翻转 / 滚动复位」→「重启恢复位置」那节的「停在原位置」条
- 列表涨长不会自己回去 ⇒ 取够页后界面**自己滚回**要恢复的位置
  - 当前位置已经不小于它、或这一层没那么长时不动
  - **下拉更新与重试后按当下位置重算**，否则在顶部刷新会被拽回上次恢复的位置
  - 这一滚同样带上面那条**顶部留白的折算**（落点仍是项序号，偏移只吃掉留白）

**代价**：

- 直取层的**整层列目录不再写这份内存快照**
  （同一 (容器, 排序) 上，整层与第 0 页共用一个键而长度差一个数量级，
  写进去会让方向切回正向时首屏按整层长度取页、发 ⌈N/每页⌉ 次请求）
- 因此**反向**在直取层上、**且这个键还没被第 0 页写过时，没有内存首帧**：
  先显示「加载中…」，等这次整层列完才上屏
  - 反向每次进来本来就要整份取完再倒过来，请求数不因此增加
  - 这个键被正向第 0 页写过时仍给出一帧，只是长度 = 第 0 页
- 正向不受影响（第 0 页那一帧照旧）
- 这一条也是上面「提前装好目标层的快照」段里「新屏出生当帧就有内容」的适用范围限定
- 要让两种方向各有各的键，得把方向带进 `Source` 的内存快照接口（方向现在算展示层概念），留作新决策

**反向仍是整份取完再倒过来**（按需加载只对正向成立）：

- 方向是展示层概念、作用在整份列表上（见「排序在展示层翻转」）
- 追加页只能往尾部接，复现不了「从尾到头」

### 封面

**取哪一张**：

- 书 = 第一页
- **本层有图的容器 = 本层首图**
- 多子文件夹的文件夹 = 逐级下取
  - **每一层都与单层目录同一套优先级**——本层图 → 本层首个压缩包的首帧
  - 每层只开首个包，同层其余包不碰

**预取**：

- 封面**字节**由界面按需取
- 列表/柜页对**可见区 ±1 屏**内、**且封面走来源字节通路**的条目**主动预取**
  - **一次最多向来源要 4 张**：屏幕上正显示的那几张优先，预取让位；已经在要的不打断
  - **一次最多解 2 张**：屏幕上正显示的那几张优先，预取让位（给画面刷新留核）
  - 预取**一批最多派 4 条任务**（`CoverPrefetch.MAX_CONCURRENT_LOADS`），与上面两个上限各自独立
  - 划出屏幕的封面不立即丢弃
  - 走 uri 解码的本地/SAF 封面行不预取
- 预取 = 取回封面图并解好存进封面图内存，与屏幕上那一格用同一把缓存键（屏幕上直接拿来用，不重解、不重取）

**何时发生**：

- **容器封面的逐级下取与压缩包首页封面的解出都只在按需取封面时发生**，
  列目录时一次都不发生
- 缓存分三层：
  - 压缩包封面解出的首页按「node.id + 修改时间」**落盘**缓存
  - 所有封面字节（含目录/容器封面）另有**本次打开 APP 期间的内存字节缓存**
    （键含条目 id 与修改时间，条目数与字节数双上界，手动刷新与来源实例释放时清空）
  - **已经解好的封面图**另占一份进程内存（与页面的图分开两份、各算各的）
    - 总大小按堆内存的 **1/8**（装得下一屏）：一屏网格封面约 12~18 张、每张约 **1.5MB**（768×1024 像素、两字节一像素）
    - 放不下时先丢最久没用的那张；屏幕上正显示的那几张不丢（显示时标「正在用」、离屏取消，
      代码里是 `pinCover` / `unpinCover`），必要时允许暂时超一点（最多 = 屏幕上的封面数 + 1）

- 问「这个子目录是不是书」时顺手拿到的「目录内首图」直接当封面用，不再重复列同一目录

**容器行封面兜底（Komga）**：

- 取不到缩略图的容器行（类别行、收藏行等）按**本地 Windows 名称序**（与列表同一套比较器）取**第一个子项的封面**
  （候选取服务端名称档的一页 500 条，超出这一页的条目看不见、按服务端序退化）
- 子项也没有则留空
- 该封面**不随全局排序变化**
- 收藏内容非纯系列时，其**内容行**也按同一套本地 Windows 名称序重排（封面与列表第一行因此是同一本）

**Komga 源取哪一张**：

- **书封面 = 第 1 页原图**（`GET /api/v1/books/{id}/pages/1`），**不带任何查询参数**
  （带 `convert=webp` 会让整屏 Komga 封面全灰：该服务器的 `convert` 枚举只有 `jpeg|png` ⇒ webp 回 400）
- **系列封面 = 该系列按本地 Windows 名称序第一本书的第 1 页**
  （列表显示用的就是这一套；服务端 `titleSort` 字符串序只用来取候选页、不作依据——它会挑到另一本书）
- 容器行（类别 / 收藏）仍按上面的兜底链取第一个子项的封面
- **不再用服务端的 `/thumbnail`**：它按**高 300px** 固定生成（宽 200–217），
  而**测试设备**（屏宽 ≈1272px）上网格 2 列的解码宽度是 **576px** ⇒ 放大 **2.7 倍**，这就是 Komga 源封面糊的来源
  （576px 是那台设备的桶值：屏更窄/更宽时按同一套分桶规则算出别的数，代码里没有这个常量）
- 代价：
  - 字节变大（每张从几十 KB 到数百 KB 级；一张 1272×1800 的页 **429,892 字节**，解码冷 613ms / 暖 22ms；
    —— 量它那条用例单一跑 1m26s–1m45s ⇒ **不进套件**）
  - 长条漫首页要按显示盒裁剪解码（裁剪解码就是为这类源做的）
  - **容器行（系列 / 类别 / 收藏）每跳多一次 list 请求**：取封面要「先 list 出名称序第一项、再取它的第 1 页」，
    以前走服务端 `/thumbnail` 时是 1 次请求
  - **会话级封面字节缓存的字节上界从 8 MiB 提到 32 MiB**：`core/source/CoverByteCache.kt` 的上界是条目 64 / 字节 **32 MiB**
    （按上面的字节量级，8 MiB 只装得下约 15~19 张、一屏 12 张就顶满，冷启动头几秒必然重取；
    32 MiB 装得下约 60~78 张 ≈ 4~5 屏。条目数上界 64 与它同量级（64 × 430~537 KB ≈ 27~34 MiB）
    ⇒ **哪一边先触顶取决于封面字节大小**，两档的实际容量都在 60 张上下）

**封面在两种视图里怎么缩放**：

- 列表视图：封面按自己的宽高比铺满左侧那一条（宽 56dp），高度跟着比例走，整张显示、不裁
  - 图还没解出来时先按一个固定比例占位，免得列表上下跳
- 网格视图：所有格子一样大
  - 格子宽 = 屏宽按列数等分；格子高 = 格子宽的 4/3（固定值，与封面自己的比例无关）
  - 封面铺满格子：短边填满、长边裁掉
  - 因此任何比例（含超长条漫页、超宽跨页）都不改变格高、不留灰边、不出现「半截」
  - 格子高最多到「屏高减去书名那一行」（横屏 2 格等场景），
    超了就让封面等比缩小、水平居中（比例仍 4:3、不拉伸），书名始终看得见
- 两种视图都按当次显示宽度取图，宽度向上取到 32 的整数倍（宽度差一点的两格因此共用同一张图）
- 封面比例超出 0.6–1.6 时按边界值裁剪（列表视图专用）；网格视图一律裁剪填满

**封面怎么出现**：

- 两步：先深灰底占位（图还没解好时显示的盒子底色），图到位后用 150ms 淡入
- 例外：图在排版那一刻就已经在内存里（比如刚从子目录返回、这一张刚才解过），第一帧直接是图，不出现灰底也不淡入
  - 判定只看这一次排版时有没有命中内存：同一个格子里重新排版不算；
    重新进入这一屏（重新进屏、换目录、转屏、格子被回收后滚回来）才算
- 淡入看不看得出来、两种状态是否统一，单测覆盖不到，只能在真机看

**只解要显示的那一段**：

- 先读源图尺寸，算出显示盒在源图上对应的那一条（居中），只解这一条
  - Android 9 及以上：裁剪与缩放一步做完
    - 裁剪的目标尺寸不能改小——目标尺寸和裁剪框是一套对应关系，改小就取不到那一条
  - Android 8.0/8.1：退回「只解那一条、再缩到显示盒宽度」（只缩不放）
- 走这条近路要同时满足四条：
  1. 这一条确实比整张少像素
  2. 留下的图比整张按比例缩小解更小
  3. 解的那一下内存峰值不超过 12.8MB
  4. Android 9+ 的那条近路同时比另外两条都轻
  - 前三条任一条不满足，就退回整张按比例缩小解（第 4 条只决定两条近路选哪条）
- 留下的图从不比改动前更大
- 上面那个峰值只算解码器要建的图，设备整体内存峰值没量
- 阅读菜单的预览条与三档字号层级见 `docs/spec/reader.md` 的「阅读菜单与预览条」

**扫描网点去斑（先去模糊再缩小）**：

- 有些封面是实体书扫来的，图上带着很密的规则网点（验收源网点间距约 5px）。
  缩到书柜格子那么大时，这些网点会被算成一片一片的灰斑——
  封面文件本身是干净的，斑是缩小时算出来的
- 做法：把「先轻度模糊、再缩到显示盒」合成一步做（不是先解出那一条、再单独模糊、再单独缩小）
  - 什么时候启用：缩小比例（源上那一条的宽度 ÷ 显示盒宽度）达到 1.5 倍；不到就完全按原样解，
    一个像素都不差
  - 模糊多重：约为缩小比例的 0.4 倍（例如缩 2.5 倍就模糊 1 倍）
  - 一行一行地读源图、只把这一条里的像素读一遍，不需要能就地改写的图，也不多占一张中间图
  - 比例本来就等于显示盒比例的封面也能走这条（按输出像素取窗口就行）
  - 内存：同时在世的只有「源图」与「显示盒」两张，不超过 12.8MB；
    像素特别多的源（长条页）不走去网点，仍走原来的退路（裁剪解码 / 整张缩小解）
  - 只作用封面；阅读器的页解码不变
- 是否启用与模糊倍数是算出来的（一条纯函数），由单测锁定
- 真机日志怎么看：`coverSource` 行里的 `plan=descreen|region|full` 与 `descreen=off|sigma=N`；
  另有 `coverDescreen` 行报 `applied=true|false`（false = 本该去网点但真机没执行）

### 列表取数性能

**每层目录只列一次**：

- 文件源（本地/SAF、SMB、WebDAV）每层只列一次目录；子目录「是书还是文件夹」要并发问，且有并发上限
  - 单条问失败就当文件夹，不拖垮整张列表
  - 断链 / 认证失效这类故障不吞：原样往上抛，不伪装成「都是文件夹」
- 同一目录这次打开 APP 期间再进来，直接用已有快照（来源实例按连接复用）
  - **快照按容器一份、与排序方式无关**——换排序不重新列目录
  - 列目录时顺手拿到的文件信息留着用 ⇒ 按名称 / 修改时间排序时不用再读磁盘
  - **发布时间档**在这次列目录里读压缩包内的 `ComicInfo.xml`，每个条目只读一次、按「条目 id + 修改时间」记住
  - **从落盘快照恢复出来的条目**（没有文件信息）在后台列目录回来之前，用快照里的修改时间顶着，**不问也不开包**
- 文件改动按容器的修改时间失效（命中时比一次，和条目数无关）

**修改时间变了也不整层重问**：

- 仍然只列 **1 次目录**，把新结果与上次快照（内存或落盘的）按「条目 id + 该条目自己的修改时间」比
- 新增 / 删除 / 改名直接反映
- **子目录自己的修改时间变了只重问那一行**，没变的行**沿用上次结论、0 次问**
  - 两边都拿不到修改时间的层（SMB 共享根、部分 SAF/WebDAV 层）当作「没变」
- 问失败的结论一律不留着用，只重试失败的那几条

**手动刷新 = 浏览页顶部下拉**：

- 只认拖拽，滚轮不触发
- 做的是清掉该容器缓存、重取容器 / 压缩包封面（本地图片封面走 uri 解码，不重取）
- **它是强制路径：清了缓存 = 下次进来整层重列 + 全量重问**；上面那套「只重问变化的行」只用于自动失效
- 同时清掉该容器**内存里的与落盘的**快照

**上一本 / 下一本**：

- 判定复用同一份快照、**只读**；没命中时不列父层、也不问子目录
  ⇒ 这个容器本次打开 APP 期间没列过时，两侧都是「没有」，界面照故事 28 显示「无上一本/无下一本」
- 进阅读器后界面在后台补齐该层
- **缓存失效只看容器自己**的修改时间 ⇒ 只改子目录**里面的内容**不会自动反映
  （要么下拉刷新，要么等父目录自己的修改时间变了触发增量重问）

**列表快照落盘**（键 = 连接 id + 容器 id，存在 APP 私有缓存目录）：

- 内容 = 条目清单 + 该目录自己的修改时间 + 写入时间 + 格式版本号，**不存封面图**
- 退出 APP 后再进同一目录：
  - 修改时间没变 ⇒ **0 次列目录、0 次问**
  - 修改时间变了 ⇒ 先用快照把列表显示出来，再 **1 次列目录 + 只重问变化的行**
- **先显示的那一帧就是快照**，界面先落它、再落重列结果 ⇒ **悄悄换掉**：不闪空白、不打断滚动
- 每条快照 **7 天有效**（看写入时间，不是最后使用时间）
- **拿不到修改时间**（离线 / 服务器连不上）也照样用快照把列表显示出来
- 连接被编辑或删除时，清掉该连接名下全部快照
- 容量上限 **2000 条或 20MB**（先到者为准，最久没用的先丢）
- 格式版本号对不上就整片作废重来，不崩

**提前装好目标层的快照**：

- **从阅读器返回浏览页不重建浏览页**（浏览层在阅读器期间常驻，见 `docs/spec/shell.md`「导航过渡」）
  ⇒ 返回时列表与位置原样就在，没有首帧要填、不会闪「加载中…」
- **换屏前提前装目标层的快照**—— 满足下面三条：
  1. 只在**这四类导航**前装：点条目下钻 / 进连接根层 / 启动重建 / 鼠标前进侧键
     （前进侧键从阅读器过来时是滑入过渡，提前装一样成立）
  2. 装的是**目标层**存在手机上的快照（只读本地：不列目录、不去问）；装错层会让新屏显示别层的内容
  3. 装快照与导航本身**同时只有一个在跑**（进程内一把公平锁），因此两次快速点击的先后 = 点下去的先后
  ⇒ 新屏「出生」当帧就有内容。读不到（来源还没好 / 没有落盘快照，如 Komga）就当没做
- **不在这四类里的两跳**：换书（没有目标浏览层）与返回上级 / 系统返回（系统弹栈，没有应用层导航入口；
  它的首帧照旧来自该层此前列目录留下的快照，**例外见上面「浏览列表按需加载」的「代价」段**）；
  总述见 `docs/spec/shell.md` 的「导航过渡」段
- **代价**：导航前多一次读本地快照（在 IO 线程）；该层第一次列目录时 `snapshotSource=` 可能标成 `memory`
  而不是 `disk`（写它的是这次提前装、不是列目录）；「0 次列目录 / 0 次问」不变
- **例外**：直取层的反向不写这份内存快照，见「浏览列表按需加载」那节的代价段
- 这个入口**绝不读磁盘**（在排版时被调用）

**冷启动（进程重启）首帧**：仍走异步，但分两段——先由快照给出一帧（0 次列目录、0 次问，只读本地文件），
再落新列目录结果 ⇒ **「加载中…」期间不再列目录 / 不再问**。四个来源一致。
  - **Komga 用的是内存快照**：只在内存、不落盘、不含修改时间，**不是**词表里的「列表快照」，
    **冷启动没有它**，见上文「浏览列表按需加载」
  - 键含排序方式

### 列表首屏与封面后到

- 封面还没出来，列表就能看、能点
  - 封面提前准备：屏幕上下各多备一屏（取回图片并解好）；屏幕上那几格按需取
  - 具体上限见「封面」条
- 封面晚到不影响名称显示和点击
- 但整个列表要等所有子目录都问完「这是书还是文件夹」才一次给出来
  （一边查一边出列表不做，见 Out of Scope）

### 列表条目长什么样、显示不显示页数

**一行里有什么**：

- 只有封面 + 名称（长名称最多两行）
- 没有「文件夹 / 书 · N 页」这种副标题

**进度条**：

- 读过的书：条在**名称正下方、与名称左缘对齐**（右端到名称列右缘，不内缩）
- 网格视图：条**压在封面下缘、不占布局**
- 没读过的书：两种视图都不画，也就不留空白
- 条的样式两种视图一样：轨道用**主题前景色、30% 不透明**；两端**方头**；高 **6dp**；不画末尾的小圆点
- **网格视图**的条下面还垫一层**黑色 45% 暗底**
  （与条同宽同高、压在封面下缘、不占布局；列表视图没有；没读过时暗底和条都不画）

**页数**：

- 文件源列目录时**不为了页数**去读压缩包中央目录、也不为页数去列子目录
- 列表里的页数一律空着；页数只在打开书之后才由书本身给出
- Komga 的页数服务器会顺手返回，但界面不显示

### 排序在展示层翻转

**排序方式与方向分开**：

- 来源接口只认排序方式，不认方向（`Source.listEntries` 的约定不变）
- 方向由界面来：按全局排序设置，把来源返回的整份结果**倒过来**再显示
- 四个来源因此行为一致（例外见故事 14 / 15）

**设置存在哪**：

- 全局排序设置（形态与选项见故事 14）存在 SharedPreferences（`ui/SortSettingStore.kt`）
- 条目列表只剩浏览页一处，所以它管浏览页的排序
- 「上次停留的位置」只记目录层级，换排序不改它

**「记住滚到哪」只有一处实现**：位置模块 `ui/BrowseScrollPosition.kt`，界面（`BrowserScreen` / `AppNav`）
只调它的六个入口（排版时进屏问一次 / 首屏交回当下读数 / 离开记一次 / 真正离屏结束这次进屏 /
开机交回该落的那一层 / 位置已放回）。记录按「（连接 + 容器）+ 一轮复位」分组。三条细节：

1. 「离开」分两步：先记一次，真正离屏（`onDispose`）再结束这次进屏；切后台只记一次、不结束
2. 切后台那一次取**当下那两份滚动状态**；写点和状态同一个键，换一轮复位就重新登记
3. 强杀 / 闪退这类没有离场回调的退出，只能靠上面那一次落盘；读数过期（已经换了一轮复位还在用旧状态）时，
   旧位置会被当成用户位置写进新一轮的记录，重启就落回换排序前的位置

**换排序设置 ⇒ 浏览页两档都回到顶部**：

- 触发只有两个：**写入排序设置**，以及**长按排序按钮**请求跳顶；**重新点当前已选的那一项**
    （设置值与方向都没变）也复位，版本号在 `SortSettingStore.revision`
  - 长按顶栏「排序」按钮 = 回顶部（点按仍是开菜单）：不弹菜单、也不改设置，只把上面那个版本号 +1
    ⇒ 与写入排序走同一条路，这一层的位置记录一起作废（入口只有浏览页与柜内那一层，柜列表不给）
  - 列表视图与网格视图各有一份滚动状态，各自复位
  - 换排序类别会重新列目录，新顺序落地那一帧再复位一次

**同一次启动内：导航不复位，重启是例外**：

- 同一次启动里，不是换排序的**导航**都不复位：下拉更新重列、切视图、进子目录 / 返回上级，
  都保持原位置（长按排序按钮的跳顶请求不是导航，按上一条复位）；从阅读器返回不重建这一屏、位置原样就在
- **重启**分两种：
  1. 落地层**不是**记录里那一层 ⇒ 那条记录**当场丢掉**（见下一条），之后走进记录那一层也**不会**恢复重启前的位置
  2. 落地层**正是**记录里那一层 ⇒ 出现「**离开这一层、再从上一级进来 ⇒ 回顶部**」，
     但要下面两条同时成立才登记（只成立一条不算）：
     1. 写盘的那一层就是**此刻所在的这一层**
     2. 记录里那一层**已经不在当前这条浏览链上**
     两条只看「连接 + 容器」和浏览链，与容器 id 什么形态无关（本地目录路径与服务端 id 一视同仁）
- 落地层上「进 / 出子目录」仍保持原位置（从阅读器返回不重建这一屏，位置原样就在）：
  - 进阅读器时写盘的是落地层自己（浏览层被盖住那一刻它自己那条写点）⇒ 被「落地层自己写盘不算离开这一层」那句提前返回挡住，两条根本没被看
  - 进子目录时当前层是它的子层 ⇒ 上面第 1 条成立，但落地层自己**还在链上** ⇒ 第 2 条不成立
  - 出子目录回本层同理（写盘层就是本层，同样被那句挡住）
  - 只有**退回上一级**会让上一级成为「当前层」并写盘，而那一刻落地层已不在链上 ⇒ 两条同时成立
- 作废只发生**一次**（再进来那一次起就回到「保持原位置」）
- 这条还依赖一个**顺序前提**：上一级那一层得**真的排版过并写盘**（`BrowserScreen` 的首屏写点），
  才有那一次登记；少了这次写盘就退回「保持原位置」（离开落地层后没在上一级停住、直接去了别处即这种）
- 两种覆盖不到的情形（实现如实如此）：落地层是**根层**时这条永不触发——根层之上那一级不是浏览层
  （书柜 / 设置等入口），没有浏览层会以「当前层」的身份写盘；
  登记也**不看去向**——只认「当前层写过盘」，
  所以从落地层回上一级再转去别处（如书柜）后回来，一样会登记（这种去向不在本条规则管的范围内）

**重启恢复位置**：滚动位置**单独落盘一份**
  （`ui/BrowseScrollPosition.kt` 写进 `BrowseScrollStorage`），只存「上次停留那一层 + 该层位置」这**一条**、**用完就清**
  （用掉 = 本进程内只喂启动那一代那一次；盘上那份留着给**下一次**重启）：
- 还没走到「启动落地」那一步时（系统还原回退栈、界面先排版那一帧），问的正好是记录里那一层就先给值，
  此时不消费、不销毁，留到交回之后再收口
- 「启动落地」定下来的那一刻收口：落地层就是记录里那一层 ⇒ 停在原位置；落地层不是 ⇒ **当场丢掉**那条记录，
  之后走进记录那一层也不会再恢复重启前的位置（「重启后只有落地那一层有记录」）
- 落在记录那一层时，那条记录**只喂启动那一代**：收口之后本进程内不再交给任何层
  （收口只发生在那条记录指向的落地层上）；用掉之后，只有「离开这一层、再从上一级进来」这一种去向
  会作废这一层的位置记录 ⇒ 回顶部（两条见上面「重启」那一段）
- 「滚动位置不落盘」这条已作废，见 `docs/SPEC.md`「Out of Scope」
- 排序与位置都不放进 `BrowseLocation`（它只记目录层级）

**「停在原位置」怎么落**：位置 = **项序号 + 纵向偏移**两项坐标——把列表**顶部那段留白**折算进偏移
⇒ 被恢复那一项**封面的顶边贴着视口上沿**，上方不露上一行（名字 / 封面）的任何像素。
留白**本身不改**（12dp 是排版要的：格子槽高与格内几何都由它定）。两条边界：
- 网格视图有顶部留白（`GRID_CONTENT_PADDING_VERTICAL`，现在由位置模块一处给出：
  容器的 `contentPadding` 与落点偏移共用 `browseTopContentPadding`），由偏移吃掉
  （`Lazy` 的 `viewportStartOffset = −顶部留白`；按「项序号 + 偏移 0」落会停在留白下面）
- 列表视图没有顶部留白（`LazyColumn` 不设 `contentPadding`）⇒ 偏移恒为 0；落在第 0 项时也不吃留白
  （那 12dp 正是「停在顶部」的边距）

这条对**本次启动内的恢复**（进出子目录 / 返回上级）与**重启恢复**是同一份：
两种视图滚动状态的初值与「取够页后滚回去」都带它（实现见 `ui/BrowseScrollPosition.kt` 的 `restoredLandingOffsetPx`）。
**滑条拖动的落点**也用同一份（`ui/QuickScrollBarOverlay.kt` 的 `quickScrollBarLandingOffsetPx`：
留白那一段调同一个函数，再加一段拖动自己的行内偏移）。
