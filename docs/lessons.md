> 时间：2026-09-17 ~ 2026-09-18 ｜ 范围：GitHub issue #25–#38（14 票）+ 终审发现的 #40–#41（2 票）

## 1. 背景与任务目标

**目标**：把 14 条可用性/性能/清理请求（triage 后落在 issue #25–#38）逐票实现、评审、合并，最后再做一轮整体复核。

**做法**：用 `serial-implement` 编排技能的形态，但按本机条件做了降级：

| 项 | 实际取值 |
|---|---|
| 分支 | `feat/usability-batch-25-38`，起点 `8562d7d`（master） |
| 泳道 | **1 条**（严格串行）。技能默认 3 条并行 → 降级原因见下 |
| 每票流程 | 独立票分支 → coder 实现 → **双轴**（spec / standards）只读评审 → 修正 → 复评 → `--no-ff` 合并 + 全量套件 + 字节级核查 → 关票写账目 |
| 最终结果 | **16/16 票关闭**，GitHub 上 0 个 open issue；**57 类 / 446 用例 / 0 失败**（起点 45 类 / 372 用例）；112 文件 `+5964 −3461` |

**为什么降级为串行**（当时记录的判断，后来被验证是对的）：

1. 本批票据多为**链式依赖**（#31 依赖 #33、#36 依赖 #31…），「coder 领先一票」在依赖链上不成立；
2. 单工作树，子代理不支持 per-child cwd，两条写泳道会互相踩；
3. `reviewer` 代理是**只读且没有 bash/git**（见 §5.2），无法在独立 worktree 里自取 diff；
4. 保护一台 16GB 内存机器：一次全量 Gradle 构建峰值 ≈2.4GB，3 路并发就是 7GB 起。

**同一票的两个评审轴仍然并行**（互不见对方结论），这是质量的主要来源：34 次 reviewer 运行里，9 票被挑出过必须修的问题。

## 2. 环境与构建

### 2.1 `assembleDebug` 直接失败：PATH 上只有 JRE，没有 javac

**现象**

```
> Task :app:compileDebugJavaWithJavac FAILED
> Could not create an instance of type org.gradle.api.internal.tasks.compile.JdkJavaCompiler
   > Could not generate a decorated class for type JdkJavaCompiler
      > com/sun/tools/javac/util/Context
```

**原因**：机器 PATH 上只有 `C:\Program Files\Zulu\zulu-21-jre` 与 `zulu-25-jre`（**JRE**，没有 javac），`JAVA_HOME` 为空。项目里**没有任何 `.java` 源**，但 AGP 仍会注册并执行 `compileDebugJavaWithJavac`，于是构建 JVM 里找不到 `com.sun.tools.javac.*` 就炸。而 `compileDebugKotlin` 单独跑是成功的 —— 所以这个问题只在「全量验收命令」下暴露。

**解决**：机器上其实装了 JDK（`D:\Software\zulu21.38.21-ca-jdk21.0.5-win_x64`，`javac 21.0.5`），把它写进**用户级** Gradle 配置（机器路径不进仓库）：

```properties
# C:\Users\<用户>\.gradle\gradle.properties
org.gradle.java.home=D:/Software/zulu21.38.21-ca-jdk21.0.5-win_x64
```

**教训**

- 「Kotlin 项目不需要 JDK」是错觉：AGP 的 Java 编译任务需要 javac，验收命令一定会踩到。
- 环境类问题要**先确认失败任务名**（`grep "> Task .* FAILED"`），不要一看到 build failed 就去改代码。
- 机器相关的路径写**用户级**配置（`~/.gradle/gradle.properties`），仓库里不落绝对路径。

### 2.2 Gradle / Kotlin 常驻 daemon 吃内存

**现象**：构建结束后仍有 2~3 个 `java.exe` 常驻，占用数百 MB 到 1GB+。

**原因**：Gradle daemon 默认空闲 3 小时才退出；Kotlin 编译另有独立的 `KotlinCompileDaemon`，即使关掉 Gradle daemon 它也照样挂后台。

**解决**（仓库 `gradle.properties`）：

```properties
org.gradle.daemon=false
kotlin.compiler.execution.strategy=in-process
org.gradle.jvmargs=-Xmx1g -Dfile.encoding=UTF-8
```

验证方式：强制重编（`--rerun`）后采样进程，确认**只有一次性的 Gradle JVM**、没有 `KotlinCompileDaemon`，且构建结束后 java 进程归零。

**教训**：多进程构建体系里「关一个 daemon」不等于关掉后台。**按进程名/命令行采样**才是证据。

### 2.3 `-Xmx` 不等于 RSS（内存上限降低 ≠ 进程只用这么多）

**实测**（同一验收命令，构建 JVM 峰值 RSS）：

| 配置 | 构建 JVM 峰值 | 测试 worker | 说明 |
|---|---|---|---|
| `-Xmx3g` | 2317 MB | 382 MB | |
| `-Xmx1g` | 1912 MB | 391 MB | 只省约 400MB |

**原因**：RSS = 堆 + 元空间 + JIT + 线程栈 + **内存映射的 jar** 等；`-Xmx` 只约束堆。测试 worker 另有自己的堆（Gradle 默认 `maxHeapSize=512m`），不受构建 JVM 的 `-Xmx` 影响。

**教训**

- 汇报内存占用时，说清是**堆上限**还是**进程 RSS**，别混。
- 想省内存要同时看：构建 JVM 的 `-Xmx`、Kotlin 编译是否 in-process（会占构建 JVM 的堆）、测试 worker 的堆。
- 其中一部分 RSS 是**文件页（映射的 jar）**，系统可在内存紧张时丢弃 —— 实际压力小于数字表面值。

## 3. 版本控制与文件编码

### 3.1 工作区是 CRLF，按 `\n` 做文本替换会「静默替换 0 处」

**现象**：用 python 脚本做「停用迁移里的某条 SQL」做红证，脚本打印 `替换处数: 0`，但脚本没报错，红证白跑一轮。后来又一次因为同因失败。

**原因**：仓库声明 `* text=auto` + 本机 `core.autocrlf=true` → **工作区文件是 CRLF**，脚本按 `\n` 拼的 pattern 匹配不上。

**解决**：脚本按真实行尾匹配，或干脆改用结构化编辑工具（会自己处理行尾）：

```python
# 读/写都保留原行尾
s = io.open(path, encoding="utf-8", newline="").read()
s = s.replace("                pageCount = null,\r\n", "                pageCount = archiveEntries(arc).size,\r\n")
io.open(path, "w", encoding="utf-8", newline="").write(s)
```

**教训**：任何「脚本改代码」的动作，落地后**必须验证是否真的改了**（`git diff --stat` 或 grep）。打印出来的「0 处」是最容易被忽略的失败。

### 3.2 `git checkout -- <file>` 会连带丢弃未提交的修正

**现象**：临时把某文件改坏做红证，验证后用 `git checkout -- <file>` 还原 —— 结果**同一文件里未提交的文案修正也被一起丢了**。

**原因**：`git checkout -- <file>` 还原的是整个文件到 HEAD，不是「撤销我刚才那几行」。

**解决**：临时改动用**精确反向替换**还原（脚本替换回去），而不是 checkout 整个文件。若确实要 checkout，先 `git stash` 或确认该文件没有别的未提交改动。

**教训**：红证/实验性改动要放在**已提交的干净状态**之后做，且只用「可逆的最小手段」。

### 3.3 行尾/编码核查要看**仓库 blob**，不是工作区

**现象**：扫描工作区发现多个文件 CRLF，一度怀疑违反了「统一 LF」的约定。

**原因**：`core.autocrlf=true` 下工作区按平台习惯检出为 CRLF，而**索引里存的是 LF**（`* text=auto` 的规范化结果）。工作区的样子不代表仓库内容。

**解决**：直接查 blob：

```bash
git show HEAD:path/to/file | grep -c $'\r'     # 0 = 存的是 LF
python -c "import subprocess;b=subprocess.run(['git','show','HEAD:'+f],capture_output=True).stdout;print(b[:3]==b'\xef\xbb\xbf')"
```

**教训**：核查结论要落在**权威对象**上（这里是仓库里的 blob），否则会得到「看起来违规」的假警报，或反过来漏掉真违规。

## 4. GitHub / 工单操作

### 4.1 用脚本写 issue 评论被 404 JSON 覆盖

**现象**：一条已经写好的 Agent Brief 评论被改成了 `{"message":"Not Found", ...}` 的 404 响应体。

**原因**：脚本里用原生 Windows python 拼 MSYS 风格路径（`/tmp/...`）作为文件路径 → 写文件失败或读到空 → `gh api -F body=@空文件` 把评论覆盖成了接口返回。

**解决**：用 `gh issue comment --body-file` / `gh api -X PATCH ... -F body=@文件`，且**文件路径用 Windows 风格**（原生 python 不认识 MSYS 的 `/tmp`）；改完**回读一次**确认内容。

**教训**：凡是对**外部系统**的写操作（issue/PR/评论），都要：① 用文件传参而不是内联字符串；② 写完回读校验；③ 保留一份本地原文（便于恢复）。这次就是因为本地留了原文才能立刻恢复。

### 4.2 子代理发的评论缺约定标记

**现象**：一名 coder 自行往 issue 上发登记评论，内容正确但**缺仓库约定的 AI 标记行**。

**解决**：用 `gh api -X PATCH /repos/.../issues/comments/<id> -F body=@file` 补上标记。

**教训**：约定要**写进给子代理的 brief**（或明确禁止它们写外部系统），否则「内容对、格式错」也会发生。

## 5. 子代理编排（最容易踩的一类）

### 5.1 子代理模型必须与主代理**显式同步**（这是真 bug，不是配置洁癖）

**现象**：连续多轮子代理失败，报错却是「额度用尽」，而主代理（我自己）一直在正常回话：

```
You've reached your weekly usage limit for your plan.
Your limits reset at ... [model=deepseek/deepseek-v4.1-flash]
```

**原因**：让子代理「继承会话模型」时，它被解析成了 `deepseek/deepseek-v4.1-flash` —— 而**主代理用的是 `opencode-go/deepseek-v4.1-flash`**（注册表里根本没有前者那个条目）。也就是说：限额挂在一条与主会话不同的部署上。

**解决**：显式传**主代理在用的那条** provider/id，并带上思考等级后缀：

```
PI_PROVIDER=opencode-go
PI_MODEL=deepseek-v4.1-flash
PI_REASONING_LEVEL=high
→ model: "opencode-go/deepseek-v4.1-flash:high"
```

**教训**

- 「继承」不等于「一致」：默认解析可能落到同名的另一条部署上。
- 派子代理前先确认 `PI_MODEL` / `PI_PROVIDER` / `PI_REASONING_LEVEL`，把它们**显式写进派发参数**，并记进编排状态文件（跨上下文压缩后仍可查）。

### 5.2 `reviewer` 代理是只读且没有 bash/git

**现象**：第一轮评审时让 reviewer「把发现写进 `.serial-implement/review-…md`」「自己跑 `git diff`」—— 全部做不到（它的工具只有 read/grep/find/ls）。

**解决**（整套流程随之定型）：

1. **补丁由编排者落盘**：`git diff <base>..<branch> > .serial-implement/diff-<票>-r<轮>.patch`，reviewer 读这个文件（大文件要分段读）；
2. **发现由 reviewer 写在回复正文里**，编排者负责落盘成文件；
3. 票面材料也落盘（`.serial-implement/ticket-<n>.md`），因为 reviewer 跑不了 `gh`。

**教训**：设计多代理流程时，先确认每个角色的**工具边界**；否则会得到「看起来完成了、其实什么都没写」的空结果。

### 5.3 子代理中断的处置四步法（本批共 9 次中断）

本批遇到的中断类型与次数（来自编排状态文件）：

| 类型 | 次数 | 报错样例 |
|---|---|---|
| 空响应 / 静默失败 | 4 | `Subagent produced no output (possible model cold-start or empty response)` |
| 运行器 worker 崩溃 | 1 | `MessagePort.<anonymous> [worker eval]:924`（被上层归成 `bash failed (exit 2)`） |
| 读越界 | 1 | `read failed (exit 1): Offset 900 is beyond end of file (141 lines total)` |
| 模型接口不可达 | 1 | `Command Code 请求失败：fetch failed` |
| 运行被替换/重载而停 | 1 | `Workflow stopped because the extension session was replaced or reloaded` |
| **计划额度耗尽** | 1 | 见 §5.1 |

**定型流程**：

```
① 先取证：git status / git log / 看子代理输出目录
② 有改动 → 立即 git add -A 并导出补丁留档（.serial-implement/wip-<票>-captured.patch）
③ 编译判断可用性（./gradlew :app:compileDebugKotlin）
④ 作为 WIP 提交保留，提交信息写明「运行器故障中断、未经评审、未跑套件」
⑤ fresh context 重试，并把上一位的「遗言」当线索交接（它在改哪个文件、卡在哪）
```

**关键设计**：派发脚本里写死「coder 失败即短路、不启动评审」：

```js
const coder = await runs.run("coder", {...});
if (!coder.ok) return { stage: "coder-failed", ... };   // ← 这条保证了 9 次中断里
const reviews = await runs.all([...]);                   //   从未产出「基于半成品的评审结论」
```

**教训**

- **失败后先看工作区**：前几次是干净的，后面几次崩前已经改了 17 个文件 —— 默认它干净会丢工作。
- 半成品要「保留但标注」：既不丢弃，也不冒充成品。
- 交接线索（上一位在做什么）能让接任者省掉一整轮诊断。

### 5.4 工具输出卫生：大输出会拖垮子代理

**现象**：一名 coder 在跑「逐测试类二分」时，一次 bash 调用挂了 240 秒（每轮约 1 分钟），并被判定需要人工干预。

**原因**：它把整份构建日志/大文件回显进上下文，且在低效二分（每次 ~1 分钟，做十几轮）。

**解决**

- brief 里加**输出卫生**要求：读代码用 `sed -n 'a,bp'` 取片段；gradle 输出重定向到日志再 `grep` 关键行；单条命令输出控制在几十行内；读文件先看行数再取片段（对 141 行的文件请求 `offset 900` 会直接报错终止）。
- 编排者用 `status` 看一眼发现「在二分」时，用 **steer** 给高信号提示（下面这条实际省了一轮）：

```
全量已跑出结果：360 tests completed, 2 failed，两个失败都在你自己新增的
BrowsingSourceSessionTest 里 → 这不是测试间污染，请停掉 pair 配对二分。
释放责任只留一个入口：单槽实例被替换时，若它正是阅读器在用的 currentSource 就不能关…
```

**教训**：子代理「慢」往往不是模型慢，而是它在做无用功；编排者的价值之一就是**打断无效搜索**。

## 6. 评审抓出的真实缺陷（这些是双轴评审的主要产出）

以下每一条都是**独立评审发现的**，且多数**不会**被常规单测或多跑几次测试发现。

### 6.1 恒真断言：测了等于没测（出现 3 次）

**现象 A**（#31）：

```kotlin
// shown 就是同一序列加了 applySortDirection(REVERSE) 的结果
assertEquals(rootBooks.reversed(), shown)     // 按构造恒真：翻转写错也绿
```

**现象 B**（#31）：用例写 `settings` prefs，断言的却是 `startup` prefs 未变 —— 两个 prefs 互不相干，**任何实现都通过**（包括「柜页又写了 lastBrowsing」的回归）。

**现象 C**（#29）：`takeIf { it.containerId == "dir-x" }` 而记录里 containerId 本来就是 null → 条件恒假。

**解决**：改成能证伪的形式 —— 固定**黄金序列**断言、**往返断言**并断言「切换真的生效」（防止空跑）、改**与基线集合比较**。

**教训**：新写断言时自问一句「**什么改动能让它变红？**」答不上来就是恒真。这类断言比没有断言更糟：它给人「已覆盖」的错觉。

### 6.2 缓存的宿主决定它是否生效（#30）

**现象**：单测里「进子目录 → 返回上级 = 0 次 list」全绿，但真机上**没有任何缓存收益**。

**原因**：列表缓存挂在 `DocumentTreeSource` 实例上，而 App **每次进页面都新建实例、离开即 close**。单测之所以绿，是因为用例自己持有一个 Source 实例。

**解决**：把浏览来源改为**会话级单槽缓存**（按 connId 复用，换连接才释放上一个），页面不再持有/销毁来源。顺带发现并修掉一个 bug：**同一实例被关两次**（`closeCount=2`，因为在协程里读 `currentSource` 而不是在同步段取快照）。

**教训**：**单元测试的持有生命周期 ≠ 生产路径的生命周期**。断言「缓存命中」之前，先问「在生产里这个缓存对象活多久」。这次修复还带来一个额外收益：导航不再每次重建 SMB 会话。

### 6.3 会话级来源带来的新副作用：构造期快照（#30）

**现象**：会话级来源上线后，往共享根/授权根新增漫画后**列表看不到**，只能手动刷新。

**原因**：根节点是**构造期快照**（`lastModifiedMs` 是构造期 val），来源一旦长期存活，根列表的「按 mtime 失效」就永不触发。此前每页新建实例掩盖了这一点。

**解决**：列目录时**只对根容器**现取一次新鲜 mtime（`resolve(rootNode.id)?.lastModifiedMs`），拿不到（SMB 共享根）就不落缓存。

**教训**：**把对象的生命周期从「短」改成「长」，必须重新审查所有「构造期快照 + 失效判据」**。这类交互效应只能靠「改动前后逐项对照」的评审，读新代码是看不出来的。

### 6.4 静默吞掉传输故障（#30）

**现象**：100 个子目录枚举中连接闪断时，界面**静默**显示「全是容器、封面全空」，不给任何失败提示。

**原因**：新写的子目录探测 `catch (t: Throwable)` 一律降级为容器，把 `TransportFailure`（本仓库有**类型契约**：网络/传输故障必须冒泡）一起吞了。

**解决**：`if (t is TransportFailure) throw t`，其余 Throwable 才降级；并补用例锁住「降级」与「冒泡」两条。

**教训**：**降级要有类型边界**。`catch (Throwable)` 是最容易把「断链」伪装成「空数据」的写法。

### 6.5 用户可见文案是「第五份文档」（#29）

**现象**：功能已改（位置不再恢复排序），SPEC、CONTEXT、ADR、代码注释四份都改了，**唯独设置页那句用户可见文案还写着「与排序方式」**。

**解决**：改文案，并在全 `ui/` 目录 grep 同类措辞，确认没有第二处。

**教训**：改动「行为语义」时，要枚举所有**口径载体**：SPEC / 术语表 / ADR / 代码注释 / **用户可见字符串**（最后一项最容易被漏，而它恰恰是用户唯一能看到的那份）。

### 6.6 往返不一致会**静默改坏**存量数据（#38）

**现象**：地址是 IPv6 字面量 + 非默认端口时，用户**打开编辑框、什么都不改、点保存** → 主机名被粘上端口、端口被打回默认，连接从此连不上。

**原因**：`formatAddress` 与 `parseFormTarget` 不是互逆的（IPv6 里的冒号与「主机:端口」的分隔冒号无法区分）。

**解决**：IPv6 加方括号（`[fe80::1]:1445`），解析侧识别 `[...]` 并兼容存量两种写法；用**往返用例表**（{主机名, IPv4, IPv6, 已带方括号} × {默认端口, 非默认端口}）逐格断言「解析结果 + 回填文本幂等」，另加 configJson 级用例锁「编辑-不改-保存后逐字段不变」。

**教训**：任何「解析 ↔ 格式化」的成对函数都要有**往返测试**（round-trip），尤其是当它作用于**用户已有数据**时 —— 这类 bug 的失败方式是「静默改坏」，不是报错。

### 6.7 并发/时序：读与写不能靠运气（#26）

**现象**：把启动判定从组合期挪进 `LaunchedEffect` + `withContext(IO)` 后，「在阅读器里退出 → 冷启动直接回到那本书」可能失效。

**原因**：同一 apply 阶段还有另一个 effect 会在 STARTUP 路由上写 `was_reading = false`；A 在挂起点挂起后主线程继续跑 B → **对同一个 prefs 键的「IO 线程读」与「主线程写」没有先后保证**。

**解决**（两步，第二步才是结构性保证）：

```kotlin
// ① 把落盘状态的读取放在 effect 体第一句、任何挂起点之前（同步完成）
val startTarget = StartupStore.startupTarget()      // 同步快照入口

// ② 更彻底：让「本会话的写」不可能落在启动窗口内 —— 写点限定在已离开中转页的路由
if (currentRoute != null && currentRoute != Routes.STARTUP) {
    StartupStore.recordReading(currentRoute == Routes.READER)
}
```

**教训**

- 「先读后写」如果依赖**调度顺序**，那只是运气；要么把读放在第一次挂起之前，要么让写**根本不可能**发生在这个窗口里。
- 评审在这里追问了一句很关键的话：「这个保证依赖 Compose 运行时行为吗？那是公开契约吗？」——**依赖非公开行为的正确性，要降级为结构性保证**。

### 6.8 `rememberSaveable` 还原导致状态机卡死（#26）

**现象**：慢启动期间旋转屏幕、或进程被杀后从最近任务重开 → 应用**停在中转页转圈**，而本票又刚关掉了该页的抽屉手势 → **应用内无出口**（改前还能划抽屉自救）。

**原因**：`startupDone` 是 `rememberSaveable`，旋转/进程恢复时会被还原为 `true`；守卫 `if (startupDone.value) return` 把「还原的入口页」误当成「已落地的入口页」→ 落地导航永不执行。

**解决**：守卫改按**还原后的当前目的地**判定（`startupDone && 栈顶 ≠ STARTUP` 才早退），并给落地流程加 `runCatching` 兜底（失败降级首页），同时**不吞 `CancellationException`**：

```kotlin
runCatching { ... }.onFailure { failure ->
    if (failure is CancellationException) throw failure      // 取消照常传播，取消后不导航
    runCatching { nav.navigate(Routes.HOME) { popUpTo(Routes.STARTUP) { inclusive = true } } }
}
```

**教训**

- `rememberSaveable` 的语义是「跨配置变更/进程恢复保留」——用它做**一次性守卫**时要问：「还原成 true 时，对应的动作真的执行过了吗？」
- 一旦**移除了用户的逃生出口**（这里是抽屉手势），就要同时保证「不可能有卡死的状态」：守卫 + 超时/异常兜底 + 不吞取消，三件一起做。

### 6.9 加密判据：前缀不够，还要看形态（#27）

**现象**：用户口令若恰好以 `enc:v1:` 开头，会被当成「已是密文」而**原样落库（明文入库）**；随后读回来又被当密文去解 → 失败 → 刚存好就提示「密钥失效，请重填」。用户重填同样的口令 → 无限循环。

**解决**：把两条路径分开，并把判据从「前缀」收紧为「前缀 + 载荷形态（合法 Base64 且 ≥ IV+tag）」：

```kotlin
// 写路径：拿到的永远是明文（读入时已 reveal 过）→ 无条件加密，不存在二次加密
fun protect(plaintext: String): String

// 存量迁移路径：处理的是已有落库值（可能已是密文）→ 跳过真密文以保证幂等
fun protectStored(stored: String): String
```

**教训**：用**值本身的内容**（前缀/魔术字节）来表达「这是什么类型」时，一定要考虑「用户数据恰好长得像它」的情况。读路径可以宽松（认不出就当密文试、失败降级），**写路径必须严格**。

### 6.10 生产密码学实现零覆盖，因为替身抄了一份布局（#27）

**现象**：`KeystoreCredentialCipher`（生产）在 446 条用例里**一次都不会执行**（Robolectric 里没有 `AndroidKeyStore`），而测试替身把「IV 前置拼接、tag 位数、无填充 Base64」又抄了一遍 —— 把拼接顺序改成 `密文‖IV`、把 tag 位改成 96，**全量套件照样全绿**。

**解决**：把布局抽成平台无关的共用件（`CredentialEnvelope`：`pack`/`unpack`/`toBase64`/`MIN_PAYLOAD_BYTES`），生产与替身共用，并加纯 JVM 用例钉住「IV 在前 / 长度常量 / 无填充 / 非 Base64 不算密文」。

**教训**：**测试替身复制了生产逻辑**时，被复制的那部分实际上就没人测了。把可变部分（布局、常量、协议）抽成双方共用的纯函数，才不会「测了替身、漏了生产」。

### 6.11 「优化」的收益必须能证明（#27）

**现象**：我把「保存连接后是否释放会话」的判定从「落库文本不等」改成「表单语义不等」，并在注释里宣称「避免了白释放一次会话」。评审指出：**会话槽的命中判据仍是 configJson 文本**，而随机 IV 让文本恒不等 → 保存仍会重建会话，这个改动**什么都没省**。

**解决**：撤销该改动，注释改成如实描述（「随机 IV 的固有代价，保存是低频动作，接受」）。

**教训**：改动收益要能**指到具体的那一行判据**上（「哪一行因此不再执行？」）。指不出来就说明它只是看起来更漂亮；这种情况下**撤销优于保留**。

### 6.12 调试探针夹带进 diff（#27）

**现象**：diff 里多出一个 `MockWsProbeTest.kt`：与本票零交集的调试探针，含**全仓唯一的 stdout 写入**（`println`），测试名是英文 `probe()`，断言与既有测试重复。

**解决**：删除；其唯一有价值的一条断言并入既有测试。

**教训**：调试残留是「崩过一次的子代理」高发产物 —— 收尾时 grep 一次全仓的 `println|System.out|printStackTrace`，能一眼揪出来。

### 6.13 触控热区回归（#40）

**现象**：为了在行尾加「删除」按钮，把 `clickable` 从整个 `Row` 挪到了名称 `Text` 上 → 触控高度从「整行含 12dp 内边距（≈48dp）」缩到「文字行高（≈24dp）」，低于最小触控目标。

**解决**：`clickable` 移回 `Row`；行内 `TextButton` 自带点击、会消费自己的事件，不需要额外处理。

**教训**：**在既有点击区域里塞新控件**时，要逐项对照「改前可点范围」，而不是只看新按钮能不能点。两个评审轴这次独立地都发现了它。

### 6.14 用「非空」近似「已加载」的判据（#40）

**现象**：删掉**最后一个**连接后，回退栈里那个连接的浏览页**永久停在「加载中…」**（且该分支没有重试入口）。

**原因**：一行纯函数用「列表非空」来近似「连接列表已加载完」：

```kotlin
// 旧：空列表既可能是「还没加载完」，也可能是「真的没有连接」——被当成前者
connectionVanished(ids, connId) = ids.isNotEmpty() && connId !in ids
```

**解决**：把两种空真正分开 —— 订阅用可空初值，`null` = 未加载、`[]` = 已加载且一条都没有：

```kotlin
val connections by dao.observeAll().collectAsState(initial = null)   // List<ConnectionEntity>?
connectionVanished(ids: List<Long>?, connId: Long) = ids != null && connId !in ids
```

**教训**：**用「集合非空」表达「已初始化」是常见近似，代价是「空集」这个合法状态无法表达**。凡是「未加载 vs 已加载但为空」会走不同分支的地方，都用 nullability 显式区分。

### 6.15 收口票会自己长出收口项（收益递减点）

**现象**：做完「去重 + 删死参数」的收口票（#41）后，评审又指出：两个 DTO 现在字段逐字同形、那个函数已退化为恒等投影；同时有 2 条测试断言在参数被删除后**已不可证伪**。

**解决**：**停手**。把这些记进票评论备查，并明确写下「收益递减，建议先合并先用，等真的妨碍改动时再动」。

**教训**：收口/重构的「完成」不是「再也挑不出问题」，而是「**边际收益低于成本**」。要敢于在清单还长的时候宣布收手，否则会无限迭代在越来越小的收益上。

## 7. 关键教训与最佳实践

### 7.1 断言必须能证伪（本批出现 3 次恒真断言）

写断言时自问：「**什么改动能让它变红？**」答不上来，就换成：

- 固定**黄金序列**（写死期望值，而不是用被测代码自身算出来的值）；
- **往返断言**（解析↔格式化互逆）；
- **先写入再断言**（不要断言「未被改动」，因为它在任何实现下都成立）；
- 与**基线集合**比较（不要用同一个表达式再映射一遍）。

### 7.2 红证（red proof）：证明测试真的在测行为

对关键行为，把测试跑在**改动前的实现**上（临时停用迁移、恢复页数统计、把缓存宿主改回页面级…），确认它**必然失败**。本批做过 4 次，每次都值得：有一次发现「脚本替换 0 处」，红证其实是空跑。

### 7.3 「登记 ≠ 修掉」

报告与评论里必须区分：**已修** / **如实登记（附理由）**。评审会核对这一点（本批评审明确写过「不要把登记当修掉」）。登记时写清：触发条件、影响面、为什么现在不做、将来在哪张票做。

### 7.4 不可自动化的部分要显式交给人

仓库没有 Compose UI 测试基建，所以「触摸/布局/观感/真机网络」类验收一律写进**票评论的真机清单**（现象 + 期望 + 为什么只能手验）。本批 16 票每票都有这样一段。

### 7.5 给子代理下指令要附「停手条件」

我要求「让 `idPrefix` 复用 `formatAddress`」，coder 核对后发现对 IPv6 主机**不等价**（会给 id 前缀加方括号 → 既有阅读进度键失效），于是按我预先给的停手条件改为只抽「端口写法」那一层，并补了等价性测试。**如果我当时只写指令不写停手条件，它很可能照做，然后进度数据静默失效。**

同理：「若你把 X 判断为不需要，请在报告里说明理由，不要静默丢弃」这条也要写进 brief。

### 7.6 文档口径是**多份**的，要一次改全

改一条语义要同时过：`docs/SPEC.md`、`CONTEXT.md`（术语表）、`docs/adr/`、代码注释、**用户可见字符串**。本批漏过一次用户可见文案（§6.5），也主动改过 ADR 与 SPEC 的口径（§6.3）。

另外：规范编号（本批的「故事 N」）一旦重排，会让全仓上百处注释失准 —— 结论是**稳定锚点**（删除留空号、新增追加，永不重排）。

### 7.7 合并闸门固定动作（每票都跑）

```bash
git diff --check <base>..<branch>                    # 空白/行尾错误
git log --oneline -1 && git status --porcelain        # 确认干净、无夹带
# 仓库 blob 的 LF / 无 BOM 扫描（不是工作区）
# 全量套件（关键票连跑两遍，排查真线程/轮询类用例偶发）
./gradlew testDebugUnitTest --rerun-tasks assembleDebug
```

### 7.8 落地后必须复核（尤其「脚本改动」与「外部系统写操作」）

- 脚本改代码 → `git diff --stat` 确认真的改了（§3.1）；
- 写 issue/PR → 回读一次（§4.1）；
- 子代理「报告完成」→ 看工作区与提交（§5.3、§5.2 里「coder 说已移除、实际是另一处」的情况出现过）。

### 7.9 编排者自己也会犯错，且同样需要被评审

`#27` 由我前台接手后，三轮评审抓出**三处我自己引入的问题**（判据只闭合一半、提示文案里的入口名不存在、一处「优化」收益不成立）。结论：**「改了」不等于「改好了」**，每条改动都要有人独立核对 —— 这正是双轴评审存在的意义。

## 8. 可复用清单（避坑 checklist）

### 开工前

- [ ] `java -version` 与 `javac -version` 都可用？（只有 JRE 时 `assembleDebug` 会失败）
- [ ] 全量套件能跑通？把结果记为**基线**（本批 45 类 / 372 用例）
- [ ] 构建是否留常驻进程？（daemon / Kotlin daemon）内存是否可接受？
- [ ] 派子代理前确认 `PI_PROVIDER` / `PI_MODEL` / `PI_REASONING_LEVEL`，并**显式传** `provider/id:思考等级`
- [ ] 确认每个子代理角色的**工具边界**（只读的没法跑 git、没法写文件）

### 每票实施

- [ ] 只做票面范围；「Out of Scope」逐条对照
- [ ] 删除/清理类改动：先 grep 出完整清单，再删；不留悬空引用
- [ ] 涉及用户已有数据的改动（迁移、解析↔格式化）：先写**往返/幂等**用例
- [ ] 加断言时自问「什么改动能让它变红？」
- [ ] 关键行为做**红证**
- [ ] 失败/降级路径要区分「传输故障（冒泡）」与「可降级错误（降级）」
- [ ] 改语义时枚举所有口径载体（SPEC / 术语表 / ADR / 注释 / **用户可见文案**）

### 交评审前

- [ ] 导出补丁到固定路径（reviewer 没有 bash）
- [ ] 票面材料已落盘（reviewer 没有 `gh`）
- [ ] 让 reviewer 把发现**写在回复里**（它没有写权限）
- [ ] 在 brief 里给「停手条件」与「不确定就说明理由」的许可

### 合并闸门

- [ ] `git diff --check` + 仓库 blob 的 LF / 无 BOM 扫描
- [ ] 全量套件（关键票连跑两遍）
- [ ] 确认无夹带（改动文件清单与票面预期一致）
- [ ] 红证结论是否仍成立

### 关票

- [ ] 新基线（类数/用例数/失败数）
- [ ] 已知边界与登记项（附理由与将来归属）
- [ ] 真机/手验清单（现象 + 期望 + 为什么只能手验）

### 遇到子代理中断

- [ ] 先取证：`git status` / `git log` / 子代理输出目录
- [ ] 有改动 → 立即导出补丁留档
- [ ] 能编译吗？（判断半成品可用性）
- [ ] WIP 提交并**标注未经评审**
- [ ] fresh 重试，并交接上一位的「遗言」线索
- [ ] 确认派发脚本里「coder 失败即短路」——避免基于半成品的评审结论

### 收官

- [ ] 整体 code-review（两轴 + Fowler 气味基线）
- [ ] 终审 findings 逐条决定：修掉 / 开票 / 登记（并写进 PR 或票评论）
- [ ] 更新 PR 正文与进度表
- [ ] **敢于停手**：当边际收益低于成本时，把剩余项记清楚而不是继续迭代
